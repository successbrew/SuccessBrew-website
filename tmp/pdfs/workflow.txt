1. Business Objective and Funnel
The system is designed around a simple business funnel: attract visitors, offer something valuable in
exchange for contact information, nurture the relationship, present a paid offer, process payment reliably,
and provision the purchased experience automatically.

Offer positioning
The discussion referenced a ₹2,999 paid resource/community offer with an MRP of ₹4,999. The exact
commercial copy, payment provider and resource contents should be finalized separately; the
architecture only assumes that a successful payment creates a customer entitlement.
Architecture principles
• Database as source of truth: user identity, lead/customer status, orders, entitlements and access state
should live in the application database.
• Brevo as marketing layer: contacts, segments, campaigns and automated email sequences should be
synchronized from the application.
• Payment provider as payment authority: the application should not trust a browser redirect as proof of
payment; it should verify the provider webhook/event.
• Access is entitlement-based: a user gets protected content because the backend sees a valid paid
entitlement, not simply because they know a URL.

Recommended automation states
A practical implementation can use states such as LEAD, ENGAGED, CHECKOUT_STARTED, PAID,
REFUNDED and UNSUBSCRIBED. The exact Brevo list/segment names are an implementation choice.
When a user becomes PAID, the lead/nurture automation should stop or branch into a customer
onboarding sequence. This prevents a customer from continuing to receive acquisition emails that no
longer match their state.

Payment states to support
• initiated: checkout has started but payment is not confirmed.
• pending: provider reports an unresolved state.
• paid: verified successful payment.
• failed: payment attempt failed.
• refunded: money was returned; access policy must be applied.
• cancelled: order was cancelled without a completed payment.
Webhook safety
• Verify the provider's webhook signature.
• Use an idempotency key/event ID so duplicate webhook deliveries do not create duplicate orders or
entitlements.
• Store the raw provider event ID and relevant timestamps.
• Treat the webhook as authoritative for payment confirmation, not a client-side success page.
• Return a successful webhook response only after safely accepting/processing the event; use
retries/dead-letter handling for transient failures.
9. Failure and Edge-Case Flows
A) PAYMENT FAILED
Checkout → Payment Failed → Show retry option → Remain LEAD/Checkout state
B) PAYMENT ABANDONED
Checkout Started → No success event → Optional reminder → Return to offer

C) DUPLICATE WEBHOOK
Webhook → Verify → Event already processed? → Yes → Ignore safely
D) PAYMENT SUCCESS / BROWSER CLOSED
Payment Gateway → Webhook → Backend → DB → Entitlement
The user still receives access later because the webhook is independent of the browser.
E) REFUND
Provider → Refund Webhook → Backend → DB = REFUNDED
       → revoke/suspend entitlement according to business policy
       → update Brevo customer segment
F) BREVO FAILURE
Backend transaction succeeds → Brevo sync fails
       → keep DB as source of truth
       → queue/retry Brevo synchronization

Important database rules
• Email should have a uniqueness strategy.
• Provider order IDs and payment event IDs should be indexed and protected from duplicates.
• Do not derive paid access solely from a UI flag; calculate it from verified entitlement/order state.
• Keep created/updated/paid/refunded timestamps for auditability.
• Avoid storing payment card data; use the payment provider's hosted/secure mechanisms.

Production concerns
• Use HTTPS everywhere.
• Keep secrets/API keys in environment variables or a secret manager, never in frontend code.
• Restrict database access to the backend.
• Configure database backups and a recovery procedure.
• Use structured logs and error monitoring.
• Rate-limit public lead/payment-related endpoints.
• Validate all external webhook requests.
• Separate development/staging/production credentials and environments.
• Use least-privilege permissions for Brevo, payment and cloud services.
